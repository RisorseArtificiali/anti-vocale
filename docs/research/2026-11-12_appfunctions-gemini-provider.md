# Research Report: Anti-Vocale as an AppFunctions/Android MCP provider for the Google Gemini app

**Date**: 2026-11-12
**Depth**: standard (official docs read in full where reachable; announcements and credible secondary reporting cross-checked)
**Confidence**: HIGH on the API surface (primary docs), MEDIUM on Gemini consumption reach beyond Samsung/OEM partners (Google's own statements are the ceiling; no independent verification of third-party reach exists yet)

## Executive answer

Yes, this is worth doing, in the specific form of "implement read-only history functions now, apply for the preview, and hold the transcription trigger until the read path is proven." The API side is unambiguously real and just matured: the Jetpack library went 1.0.0-beta01 on 2026-10-21 and 1.0.0-rc01 on 2026-11-04 (release notes, last updated 2026-11-04), and our build already compiles against API 36 (`app/build.gradle.kts` line 28), which is the one hard requirement. The consumption side is real but gated: Gemini has executed third-party AppFunctions since at least February 2026 (Samsung Gallery on the Galaxy S26; Calendar, Notes, and Tasks apps "on devices from multiple manufacturers", per the Android Developers Blog of 2026-02-25), and on 2026-10-28 Google opened the self-service Connected Apps Platform preview, whose Android MCP route is exactly AppFunctions, published through the Google Connected Console linked to our Play app. The gating that matters to us: the platform requires Android 16+ devices, preview access opens in phases (third-party reporting says US developers first, which Google's own pages do not state), and the orchestration agent may process queries and results on Google's servers, which collides with our privacy-first positioning unless we scope it as an explicit opt-in. The implementation cost for two read-only functions over `LogDao.searchAllRaw` is small; the real work is the Connected Console leg (app card, example prompts, testers, Play release coupling) and the privacy copy.

## 1. What the AppFunctions API is today (facts, cited)

### 1.1 Two layers

- **Platform API** in `android.app.appfunctions` (API level 36, Android 16 "Baklava"): `AppFunctionManager`, `AppFunctionService`, `ExecuteAppFunctionRequest`, `AppFunctionMetadata`, `AppFunctionSearchSpec`, `AppFunctionSchemaMetadata` (package summary at https://developer.android.com/reference/android/app/appfunctions/package-summary, accessed 2026-11-12). The docs state plainly: "AppFunctions is available on devices running Android 16 or higher" (overview, https://developer.android.com/ai/appfunctions, last updated 2026-07-31).
- **Jetpack library** `androidx.appfunctions` with a KSP compiler: artifacts `appfunctions`, `appfunctions-compiler`, `appfunctions-testing` (release notes, https://developer.android.com/jetpack/androidx/releases/appfunctions, last updated 2026-11-04). Version cadence: alpha01 2025-05-07 through alpha13 2026-10-07, beta01 2026-10-21, rc01 2026-11-04; a stable 1.0.0 is imminent at today's pace.

### 1.2 Programming model (developer guide, https://developer.android.com/ai/appfunctions/add-appfunctions, last updated 2026-10-20)

- Since 1.0.0-alpha10 (2026-07-01) the architecture is a compile-time entry point: an abstract class extending `AppFunctionService`, annotated `@AppFunctionServiceEntryPoint(serviceName = "...", appFunctionXmlFileName = "...")`. KSP generates the concrete service subclass plus an XML schema in `assets/`. The pre-alpha10 `AppFunctionConfiguration.Provider` approach is legacy with a documented migration path (same guide).
- Functions are `suspend fun`s annotated `@AppFunction(isDescribedByKDoc = true)`; parameters and returns are `@AppFunctionSerializable` data classes whose KDoc compiles into the schema the agent consumes. The July 2026 Android Developers Blog puts it strongly: "KDoc comments are a compiled API asset; clear parameter descriptions directly impact the execution accuracy of the system agent" (https://android-developers.googleblog.com/2026/07/build-intelligent-android-apps-appfunctions.html).
- Error signaling uses predefined exceptions such as `AppFunctionInvalidArgumentException` and `AppFunctionElementNotFoundException` (guide snippet, 2026-10-20).
- Functions run on the UI thread by default; the official examples wrap the body in `withContext(Dispatchers.IO)` (July 2026 blog).
- The guide's Hilt sample is literally our stack: `@AndroidEntryPoint` on the abstract service, `@Inject` of a Room-backed repository, Room `TaskEntity` mapped to an `@AppFunctionSerializable` return type.

### 1.3 Manifest surface

From the guide (2026-10-20): a KSP-generated `<service>` with `android:permission="android.permission.BIND_APP_FUNCTION_SERVICE"`, `android:exported="true"`, `tools:targetApi="36"`, an intent filter for action `android.app.appfunctions.AppFunctionService`, service `<property>` entries `android.app.appfunctions.schema` (an XSD) and `android.app.appfunctions.v2` (the generated function XML), plus an application-level `<property android:name="android.app.appfunctions.app_metadata" android:resource="@xml/app_metadata"/>` carrying global operational rules. Only the platform (system_server holds the binding permission) can bind the service; ordinary apps cannot call it directly (secondary but consistent with the manifest contract: Medium teardown at https://medium.com/@kaito_and_droid/android-appfunctions-under-the-hood-the-binder-journey-from-gemini-to-your-app-d292afa3211f, and the sample note that `EXECUTE_APP_FUNCTIONS` is privileged-only on Android 16 builds at https://github.com/FilipFan/AppFunctionsPilot).

### 1.4 Discovery and execution flow

Callers (agents) need the `android.permission.EXECUTE_APP_FUNCTIONS` permission, "granted only to privileged system applications" on current Android 16 builds (AppFunctionsPilot README, 2026), which is why the only realistic caller today is a system-level agent such as Gemini. The documented flow (overview, 2026-07-31): the system indexes the declared functions from the generated XML; the caller retrieves `AppFunctionManager`, checks `isAppFunctionEnabled(packageName, functionId)`, then executes with an `ExecuteAppFunctionRequest` whose parameters travel as `AppFunctionData`, a string-keyed map of supported types including primitives, lists, `ByteArray`, `Parcelable` values, and URI grants (`AppFunctionUriGrant`, with persistable URI permission flags, added alpha06 2025-11-05 and alpha08 2026-03-11 per the release notes; reference at https://developer.android.com/reference/androidx/appfunctions/AppFunctionData). Our side never implements discovery or transport; we implement functions and the system broker does the rest.

### 1.5 Runtime gating and verification

- `@AppFunction(isEnabled = false)` plus `AppFunctionManager.setAppFunctionEnabled(...)` with KSP-generated ID constants lets us gate functions per user preference or app state (guide section "Toggle AppFunction availability at runtime", 2026-10-20). One documented trap: "AppFunctions indexation may not be fully completed upon initial app startup", so enable calls can throw on a fresh install.
- On-device verification needs no agent: `adb shell cmd app_function list-app-functions` lists our indexed functions and `cmd app_function execute-app-function --package ... --function '<Class>#<method>' --parameters '{...}'` executes one directly (guide, 2026-10-20). Google also ships a testing-agent app (https://github.com/android/appfunctions) and an official Android skill (`android skills add appfunctions`).
- Minimum versions: `compileSdk` 36 or higher is required; minSdk is unconstrained because "AppFunctionManager returns an instance if the feature is supported, and returns null if not" (guide, "Version compatibility"). Our `compileSdk = 36`, `minSdk = 26`, `targetSdk = 36` already satisfy this.

### 1.6 Policy surface

Google Play has already codified AppFunctions in the sensitive-APIs policy: "AppFunctions API: Developers must ensure their AppFunctions do not deceive or manipulate AI agents, bypass security controls, or interfere with other applications", effective 2027-04-14 (https://support.google.com/googleplay/android-developer/answer/16558241, accessed 2026-11-12).

## 2. Gemini consumption reality check

- **2026-02-25, primary**: the Android Developers Blog "The Intelligent OS" states that the Samsung Gallery integration with Gemini on the Galaxy S26 series "showcases AppFunctions in action" with the worked example "Show me pictures of my cat from Samsung Gallery", that availability "will soon expand to Samsung devices running OneUI 8.5 and higher", and that "Through AppFunctions, Gemini can already automate tasks across app categories like Calendar, Notes, and Tasks, on devices from multiple manufacturers", linking Gemini help pages (https://android-developers.googleblog.com/2026/02/the-intelligent-os-making-ai-agents.html). This is Google's own confirmation that Gemini executes third-party AppFunctions in production, with OEM apps as the first wave.
- **Consumer-side confirmation**: the Gemini help page for notes lists Google Keep plus HONOR, Lenovo, OnePlus, OPPO, Samsung, TECNO, vivo, and Xiaomi Notes, managed by the user under Connected Apps settings, with confirmation notifications and Undo for list edits (https://support.google.com/gemini/answer/15230597, accessed 2026-11-12). Realme is not in that list; whether the RMX3853 on Android 16 exposes the AppFunctions registry to Gemini is unverified (open question below).
- **2026-05 to 2026-07, primary**: the developer docs overview (last updated 2026-07-31) still says "As of May 2026, AppFunctions integration with Gemini is in a private preview with trusted testers", and the I/O Connect '26 deep dive repeats "it is currently in private preview with trusted testers" at 19:48 (https://www.youtube.com/watch?v=qtQMH8RBYIo). The FAQ adds that during the experimental phase "only a limited number of apps and system agents can access the entire pipeline", which is why an unlisted app's functions are invisible to the system agent even when correctly implemented.
- **2026-10-28, primary, the gate opens**: Google launched the Connected Apps Platform preview: "Developers integrate with a cloud-hosted MCP server or Android MCP using the AppFunctions APIs, then use the Google Connected Console to register, test, and submit their app", choosing Search, the Gemini app, or both; access "opens in phases" (blog.google, https://blog.google/innovation-and-ai/technology/developers-tools/connected-apps-one-place, 2026-10-28; developer page https://developers.google.com/connected-apps). The same day the Android Developers Blog framed it as "build natively using Android MCP or remote MCP, prototype using Gemini dev mode, and register through the Google Connected Console preview program when you are ready for production" (https://developer.android.com/blog/posts/build-it-your-way-a-next-era-of-android-development, 2026-10-28). Secondary reporting on the same announcement says the preview is US-developers-first with no wider timeline (ppc.land and 9to5google, 2026-10-28; shattered.io, 2026-10-30); Google's own pages do not state a country restriction.
- **The operational path is documented**: "Create and manage Connected Apps using AppFunctions and Android MCP in Google Connected Console" (https://developer.android.com/ai/appfunctions/create-manage-connected-apps, last updated 2026-10-27) walks the full flow: create a connected app with connection type Android MCP, link it to the Play app (one connected app per Play app, immutable connection type), fill the public app card (description, capabilities, three to four example prompts that must reference the app name in specific patterns, localization via inline language tags, Terms and Privacy URLs), upload an `.aab` containing the AppFunctions, submit the connected app version, manage testers (personal `@gmail.com` accounts only, Android phone or tablet, exact submitted bundle version installed, roughly 20 minutes propagation), test via `@AppName` mentions in Gemini, and publish. Crucially: "an Android MCP connected app doesn't require a separate review or publish action on the Connected app management page. Instead, your connected app version is reviewed by Google and published automatically when you release the Play app version containing your AppFunctions app bundle to production."
- **Separate legacy track**: the docs overview also carries an Early Access Program interest form (https://forms.gle/GN5ybjQFhzHRCguM7) which predates the Connected Apps preview; the Forkast analysis (https://forkast.news/android-appfunctions-beta-does-not-mean-open-agent-access, late October 2026) correctly notes these are distinct channels and that beta API status does not by itself grant production reach.
- **Bottom line**: "Gemini actually calls it" is confirmed for a curated set (Samsung plus OEM calendar/notes/tasks apps, and 50+ connected apps across Search and Gemini as of the October launch per ppc.land). For an independent app like ours, consumption requires acceptance into the Connected Apps preview; implementing the API without that acceptance produces functions no system agent will currently invoke.

## 3. Our three candidate functions

### 3.1 searchTranscriptHistory(query -> matching rows): clean fit, recommended first

The docs' own cross-app example is this exact shape: "Search for emails matching a query or sender name... @return A list of matching email summaries" (overview, 2026-07-31). Our implementation maps one to one: `LogDao.searchAllRaw(query)` (`app/src/main/java/com/antivocale/app/data/local/LogDao.kt` line 103) returns `Flow<List<LogEntity>>`; we would map to an `@AppFunctionSerializable` row (id, timestamp, sender or source label, preview text, audio duration, model name). Constraints: return bounded lists (the agent should not ingest thousands of rows; cap at a sensible page and offer a get-next or narrower query pattern), and expect the returned transcript text to leave the device (see privacy below). Verdict: expressible today with no API gaps.

### 3.2 getTranscript(id or "most recent voice note"): clean fit, recommended alongside

The notes-app pattern in the docs (create, edit, list notes) plus `AppFunctionElementNotFoundException` for missing ids covers this directly. "Get the transcript for the most recent voice note from X" is the highest-value phrasing for our user base; it needs a small query helper (most recent by timestamp filtered on type/status) plus the full-text return through the SubtitleFormatter entry pair for speaker-annotated text, per the CLAUDE.md rendering contract. Verdict: expressible today.

### 3.3 transcribeAudioFile: expressible but the wrong shape for now

The contract can carry it: parameters arrive as `AppFunctionData` including `ByteArray` and URI grants (`AppFunctionUriGrant` with persistable URI permission flags exists precisely for cross-app file access, per the release notes alpha06/alpha08 and the `AppFunctionData` reference). But three frictions make it a poor first function: first, an agent would have to obtain the audio (from another app or the file system) and hand us a URI, a flow no Gemini-side behavior document confirms today; second, transcription is minutes-long and our engines load 600 MB to 2 GB models, while the AppFunctions model is short suspend calls inside a bound service, so we would be fighting timeouts and process-death semantics that the docs do not address (the guide is silent on long-running executions; that silence is itself the finding); third, the correct product shape probably reuses `InferenceEnqueue` and returns a handle or a `PendingIntent` result (PendingIntent returns exist since alpha08) rather than blocking for the transcript. Verdict: possible later, hold until 3.1 and 3.2 are live and the execution-time story is documented.

### 3.4 Privacy and security constraints (what the docs actually say)

- Execution is local: "AppFunctions... execute locally", "lets you use the existing app state directly on-device" (overview FAQ, 2026-07-31); the Connected Apps page markets Android MCP as "especially useful if apps want their tool execution to happen locally" (https://developers.google.com/connected-apps, accessed 2026-11-12).
- But the agent's reasoning may not be: "system agents may process user queries on the server to leverage advanced LLM capabilities" (add-appfunctions guide, "Considerations of types of functionalities to make available", 2026-10-20). The recommended-guidelines list that follows this sentence renders empty in every extraction I ran; the load-bearing warning stands on its own. Practically: the user's question, our function schema, and any transcript text we return can transit to and be processed on Google's servers.
- Gemini-side handling: "When you ask Gemini to do things for you, Gemini shares necessary data with others on your behalf to help complete your tasks", connected-app data may be used for personalization when the user opts in, and third-party apps process data per their own policies (Gemini Apps Privacy Hub, https://support.google.com/gemini/answer/13594961, accessed 2026-11-12).
- User control on the Gemini side: users link the connected app once (Settings and help > Connected apps, or via `@AppName`), see capability descriptions and example prompts before connecting, and get confirmation notifications with Undo for actions such as list edits (create-manage guide 2026-10-27; notes help page). The AppFunctions developer docs themselves document no execution-confirmation dialog; confirmation lives in the agent UX, not in our API contract. Where the docs are silent I am saying so rather than guessing.
- Implication for our privacy contract: our positioning is "transcription never leaves the device"; an AppFunctions history search hands transcript text to an agent that may process it server-side. This must be an explicit opt-in (default off, our own `isEnabled = false` gating plus a Settings toggle feeding `setAppFunctionEnabled`), with copy in the established voice-note-privacy style spelling out that execution is local but results go wherever the user's assistant goes.

## 4. Effort and risk sketch for our stack

- **Code (small)**: one new `transcription/` or `service/` file with the abstract `AppFunctionService` entry point, two or three annotated suspend functions, two `@AppFunctionSerializable` DTOs mapping `LogEntity`, the manifest service plus properties block, KSP plugin and two dependencies (`androidx.appfunctions:appfunctions` and `appfunctions-compiler`, both at rc01), and a `setAppFunctionEnabled` bridge from a new preference. The documented pattern is Hilt-plus-Room, which is exactly our architecture (`@AndroidEntryPoint` service, injected DAO). Estimate one to two working days including tests, because the official samples do the design work for us.
- **Verification (cheap, no agent needed)**: `adb shell cmd app_function list-app-functions` on the RMX3853 (Android 16) confirms indexing; `execute-app-function` drives the function end to end; the github.com/android/appfunctions testing agent exercises discovery too. First device check: whether ColorOS/Realme UI ships the appfunctions registry service at all; the docs say Android 16+ without OEM carve-outs, but Realme is absent from Google's own Gemini partner lists, so treat presence on the RMX3853 as unproven until probed.
- **Console leg (the real cost)**: connected app creation, app card with example prompts (the validation rules are picky: three to four prompts, at least two starting with `@AppName`, one natural mention without the at-sign, no numbered prefixes), Terms and Privacy URLs, AAB upload through a Play release, tester onboarding, then production coupling: every AppFunctions change rides a Play `versionCode` increment once a release is published, and unpublished drafts are the only iteration loop without version churn (create-manage guide, 2026-10-27). Budget a day of console work plus reviewer-latency patience.
- **Risks and known gotchas**:
  1. API churn: alpha10 (2026-07-01) replaced the entire configuration mechanism; anything we build should target rc01 and re-verify at 1.0.0 stable. Release notes are the changelog of record.
  2. Indexation race at first startup (documented exception path in the runtime-gating section); our enable-on-launch must tolerate it.
  3. UI-thread default execution; every function body needs `Dispatchers.IO`, matching our existing service-side coroutine discipline and the injected `@ApplicationScope` convention where process-lifetime work appears.
  4. Flavor split: the connected app is keyed to the Play app and its AAB; the F-Droid lane uses a different versionCode scheme (base times ten plus ABI per our release memory), and testers must run "the exact submitted bundle version". Whether an F-Droid-installed build can ever be addressed by Gemini is an open question; the safe assumption is that Gemini linking works only for Play-lineage installs, and the fdroid flavor can ship the code inert.
  5. Privacy-contract exposure as described in 3.4; also Play policy from 2027-04-14 (no deceiving or manipulating agents), low-friction for read-only functions.
  6. Preview admission is not guaranteed: access "opens in phases" (blog.google 2026-10-28), secondary reporting says US-first. The mitigation is that the code is small and the `@AppFunction` surface can ship dark (`isEnabled = false`) while admission is pending.
- **What I could not find (stated, not guessed)**: any documentation of execution-time limits for a function call; any statement of which Gemini app version or channel (beta versus stable) a tester needs beyond "Android phone or tablet"; any published admission criteria for the preview; and any real-world report of an independent (non-OEM, non-partner) app being live through the AppFunctions route, since all 50+ live connected apps predating the preview were partnership integrations.

## 5. Open questions

1. Does the RMX3853 (Realme UI on Android 16) expose the AppFunctions registry and a Gemini build that can invoke it? Probe with `adb shell cmd app_function list-app-functions` after a debug build.
2. Does Connected Console admission currently require a US developer account in practice? (Google's pages are silent; the US-first claim is secondary reporting only.)
3. How does the Connected Console Play linkage interact with our playStore/fdroid flavor split and the F-Droid versionCode scheme?
4. What execution-time ceiling does the bound-service call tolerate in practice for a Gemini invocation (matters only if we later attempt 3.3)?
5. Does Gemini surface any confirmation UI before a read-only function returns user data, or only for mutating actions? The docs do not say; device testing during the preview would answer it.
6. Will the 1.0.0 stable release change the manifest or entry-point surface again? Track the release notes before locking our implementation.

## Confidence Assessment

- HIGH: the API surface facts (packages, annotations, manifest, execution flow, API 36 requirement, library maturity curve), all from developer.android.com pages fetched 2026-11-12 with their own last-updated dates cited.
- HIGH: Gemini has executed AppFunctions in production since February 2026 and the Connected Apps Platform (2026-10-28) is the self-service route with AppFunctions as the Android MCP path; primary Google sources for both.
- MEDIUM: preview admission practicalities (phases, US-first, review depth), where the strongest details come from careful secondary reporting rather than Google's pages.
- UNVERIFIED: end-to-end reach for an independent app (nobody outside the preview has published evidence yet), Realme-device behavior, and every item in the open-questions list.
