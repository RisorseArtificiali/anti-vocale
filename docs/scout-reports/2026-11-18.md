## Finding 1: Granite Speech 5.0 2B in LiteRT-LM format

- Source: https://huggingface.co/litert-community/granite-speech-5.0-2b (conversion of https://huggingface.co/ibm-granite/granite-speech-5.0-2b)
- What: 2.3B speech-language model (16-layer conformer encoder, window query transformer, Granite-4.0-1b-based 40-layer LM, int8 weights) in `.litertlm`. ASR in English, French, German, Spanish, Portuguese, Japanese; speech TRANSLATION to English from those, and the source model also translates English speech to Italian and Mandarin. Keyword biasing via prompt ("Keywords: ...") verified in their card against the source model.
- Files: `granite-speech-5.0-2b_ekv2048.litertlm` (2,824MB, GPU-capable encoder, 116-152s of audio per message) and `granite-speech-5.0-2b.litertlm` (2,847MB, 4,096-token KV, CPU encoder, 234-307s per message; rewritten Nov 17 for GPU decode at 25.9 vs 15.0 tokens/s).
- Performance: Galaxy S26 (Android 16), LiteRT-LM 0.19.1: 9.9s clip, first text 1.21s, full transcript 2.44s (GPU LM). Peak memory 3.9GB GPU / 6.2GB CPU. Pixel 11 Pro (thermally capped): 27.7-32.5s for the same clip - the mid-range experience will be far from the flagship number.
- Quality: their accuracy check shows ~2% WER-class English results and identical transcripts across phone/desktop runs; per-language WER for de/fr/es/pt is NOT published in numbers on the conversion card (the source card carries IBM's claims). Confidence for our tradition languages: unverified.
- Constraints for us: the Nov-17 main file "was run only with LiteRT-LM 0.19.0 to 0.19.2"; we hold 0.17.1 (TASK-783 hold-and-watch). Our VibeVoice TASK-872 loop proves the runtime's audio-message API shape matches our backend's usage.
- Scores: quality 4 (langs right, numbers partial) / size 3 / on-device 3 (exact format, runtime+RAM gated) / coverage 2 (de/fr/es/pt already served; adds ja + translation) / importability 2 (LLM slot only, post-runtime-bump) / maintenance 5. **Composite 6.6/10.**
- Import path: built-in-catalog LLM entry (the Gemma lane) ONLY after the LiteRT-LM 0.19.x upgrade; then a device trial on the RMX3853 (RAM class 8-12GB fits the 3.9GB GPU profile) with our FLEURS-style spot checks per language.

## Finding 2: Parakeet TDT 0.6b Redux (sherpa-onnx packaging)

- Source: https://huggingface.co/csukuangfj/sherpa-onnx-nemo-parakeet-tdt-0.6b-redux-int8 (fp32 twin published alongside)
- What: Moondream's 1.58-bit ternary re-quantization of NVIDIA's parakeet-tdt-0.6b-v3 (same architecture and 8193-token vocab, encoder weights in {-1,0,+1} with per-128-column scales), exported dense and re-quantized for sherpa-onnx. 25 languages, `model_type="nemo_transducer"` - drop-in for our path.
- Numbers (the packager's own FLEURS eval, 300 clips/language, one harness): int8 Redux vs v3-int8 vs Ultra-int8 WER - English 13.86/11.16/8.51, German 11.00/6.84/5.20, French 10.97/8.69/7.48, Spanish 5.04/4.55/3.81, Maltese 39.74/56.41/44.74, Greek 49.46/46.64/45.19; six-language average 21.68/22.38/19.16. ITALIAN NOT MEASURED. The card's own verdict: "Pick it when the smaller download matters or the language is one where it wins, not as a general replacement."
- The int8 quantization hurts Redux disproportionately (fp32 English 7.62 vs int8 13.86; per-channel dynamic quantization cannot represent the ternary scales).
- Scores: quality 2 / size 4 (327MB int8 download, best in family; ~670MB unpacked, same as ours) / on-device 5 / coverage 2 / importability 4 (sherpa-ready transducer) / maintenance 4. **Composite 6.8/10 - but the action is nil:** our compact slot (stock int8, 640MB-class) beats it in every measured language except Maltese.
- Disposition: recorded and declined. Revisit only if (a) an fp32-package Italian number appears AND (b) a "micro download" catalog slot is ever wanted; our eval harness can settle Italian in one desktop run if that day comes.
