# TASK-954 Dutch lane: bench the ready-made Canary-1B-v2 nl int8 (GH #182)

**Date:** 2026-11-03 · **Scope:** the Dutch community-catalog lane: bench the incumbents on FLEURS nl_nl, bench the no-conversion-needed candidate `bnoordhuis/canary-1b-v2-sherpa-onnx-nl-int8` (a ready-made sherpa int8 of NVIDIA Canary-1B-v2), verify it loads on our pinned sherpa-onnx 2.0.1, and give a GO/NO-GO against Whisper Turbo. This report is a new file; nothing was committed, pushed, published, or cataloged, and no catalog entry was created (STOP point per the lane plan).

## TL;DR

The candidate needs NO conversion (encoder + decoder int8 ONNX + tokens, the exact Canary import shape `ModelFamilySupport.CanarySupport` consumes) and it WINS the bench outright: **6.08 WER vs Turbo's 8.29** on the same 40-clip nl_nl protocol (26.7% relative), while decoding **2.4x faster** than Turbo on this harness (RTF 0.163 vs 0.390) despite being a 1B-parameter model. Sherpa 2.0.1 compatibility is verified empirically: the model loads via `from_nemo_canary(src_lang="nl", tgt_lang="nl")` and produces real Dutch (not the English fallback of pre-1.13.8 sherpa). Recommendation: **GO** for the gated remainder (catalog entry + device pass); the open question is only the 1.39GB / 8GB-device RAM cost, the same wall class the fi device pass already characterized for a 1.78GB whisper.

## Source, license, and sherpa-version compatibility (the load-bearing check)

- **Source:** https://huggingface.co/bnoordhuis/canary-1b-v2-sherpa-onnx-nl-int8. An int8 ONNX export of NVIDIA's `canary-1b-v2` (https://huggingface.co/nvidia/canary-1b-v2), already in sherpa-onnx's offline-Canary file layout. The card yaml lists languages nl/en/de/fr/es; the card body claims coverage of the original model's 25 European languages (a claim, not our measurement; the entry would pin nl only).
- **License:** CC-BY-4.0 (both the export and the base model; the card asks to credit NVIDIA as creator of the original). Compatible with our catalog; attribution note belongs in the entry if we ship it.
- **sherpa compatibility:** the card documents that sherpa-onnx **1.13.8 and earlier silently fall back to English for any Canary language code outside en/es/de/fr** (k2-fsa/sherpa-onnx#3961, fixed by PR #3962 after 1.13.8). Our pin is 2.0.1 (the shipped AAR and `eval/.venv`), which carries the fix. **Verified empirically this session**, not just inferred from the fix landing: on the eval venv's sherpa 2.0.1, `OfflineRecognizer.from_nemo_canary(..., src_lang="nl", tgt_lang="nl")` loads and decodes FLEURS nl_nl_00 to correct Dutch ("Volgens Angle 2006 kunnen organisaties beter presteren met een aanpak op basis van het continuummodel."). An English-fallback or translation outcome would have been the failure signature, and it did not occur. The `tokens.txt` carries `<|nl|>` at id 62. The Android AAR is the same 2.0.1 core; the device pass remains the gated final proof.
- **App import compatibility (static):** the encoder's metadata reads `model_type: "EncDecMultiTaskModel"`, `feat_dim: 128`, `vocab_size: 16384`, `version: 1`. That is exactly what `CanarySupport.validateImportedModel` requires (the value-aware discriminator) plus the 128-mel family constraint, and the 3-file set matches `requiredRoles()`. `modelType` is ignored for canary (the app pins `OfflineModelConfig.modelType = "canary"` itself). No joiner file to trip the transducer rejection.

## Honest caveats

- **Clip mode vs the app's 10s chunking:** the app caps Canary at 10s VAD-aligned chunks (the 180M-Flash degeneration measurement, docs/research/canary-chunking-2026-08-29.md). This bench ran clip mode on whole FLEURS clips; 13 of the 40 clips exceed 10s (longest 23.1s) and the candidate still scored 6.08, which suggests the 10s degeneration wall is 180M-Flash-specific and conservative for 1B-v2. But the number measured is the full-clip shape, not the shipped chunked shape; the device pass exercises real chunking. Re-running clip mode with a hard 10s pre-cut would be off-protocol for this table.
- RTF 0.163 for a 1B model on 4 desktop threads is real but says nothing about the Dimensity's thermal or scheduling profile; the fi device pass showed a roughly 3.5x desktop-to-device slowdown class for a large whisper. The candidate's advantage is it starts 2.4x faster than Turbo on desktop, so even a large device penalty has headroom before it is worse than Turbo on-device.

## GO/NO-GO

**GO** (for the gated remainder). The quality case is unambiguous: 6.08 clearly beats every measured incumbent including Turbo's 8.29, on the standard protocol, at a faster decode than Turbo. This is not a match-at-streaming-upside case; it is a straight win on both axes the bar names. The model needs no conversion lane at all (the first catalog candidate that imports as-is), the license is fine with attribution, and sherpa 2.0.1 compatibility is empirically proven. What is NOT yet proven is the device leg: 1.39GB download and the load-time RAM spike on the 8GB RMX3853 (the fi pass measured a 705MB resident delta for a 1.78GB model plus ColorOS kills of background services; a 1.39GB canary lands in the same wall class). If the device pass fails on memory, the nl lane falls back to Turbo (built-in, 8.29) as the standing recommendation, and #182 gets the honest answer.
