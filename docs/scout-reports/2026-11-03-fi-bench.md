## Conversion record

**Source:** `Finnish-NLP/whisper-large-finnish-v3` (Apache-2.0, artifact-stable since 2024-08-01, sha b23deb0b). Full whisper-large-v3 architecture (32+32 layers, 128 mels, d_model 1280, 1.54B params), HF safetensors 3.22GB (fp32; the fp16 estimate in the 2026-10-24 report was wrong, the repo ships fp32 only).

**Toolchain (era-matched per TASK-940):** torch 2.3.1, onnx 1.16.2, onnxruntime 1.18.1, numpy 1.26.4, openai-whisper 20250625 (its `disable_sdpa`), transformers 4.44.2; sherpa sources at the pinned srclib commit af2d8d81 (v2.0.1), worktree at `/var/tmp/fi-769/sherpa-src`. Export via `export-onnx-with-attention.py` (the -attn shape the catalog now uses: 4-output decoder + n_alignment_heads metadata).

**The model-specific landmine (load-bearing for any future HF whisper conversion):** the HF tokenizer of this checkpoint is stock whisper-large-v3 with `<|yue|>` INSERTED at id 50358; every special token id from 50359 up (task tokens, no_speech, timestamps) is shifted +1 versus openai-whisper's built-in tokenizer (`<|0.00|>` is 50365 in HF vs 50364 in openai; verified by direct diff of vocab.json and added_tokens.json against openai/whisper-large-v3, which are byte-identical to the fi repo's). Converting weights without fixing this would map every timestamp and task token to the wrong embedding row. Fix: permute `token_embedding` rows into openai id order, dropping the unused `<|yue|>` row (n_vocab 51866 → 51865). The checkpoint's `proj_out` was verified exactly tied to the embedding (max abs diff 0.0), so the permutation covers the output projection too. The decoder positional embedding is a LEARNED table (std 0.0078, the turbo class, not the 0.68 sinusoid of the encoder); both positional tables are copied verbatim from the checkpoint, which is what makes that safe.

**Export patches** (in the worktree, matching the skill's list): `large-fi` added to the script's model choices with `USE_MODEL_METADATA` alignment heads, a `load_model` branch for `./large-fi.pt`, the 128-mel branch, and `per_channel=True` on the decoder `quantize_dynamic` (skill GOTCHA 2a). The `"large" in name` external-data branches already covered the fp32 graphs; torch 2.3.1 auto-externalizes graphs over 2GB.

**Validation (all run and read this session):**
- .pt vs HF pipeline agree-check (skill step 2): identical transcripts on two FLEURS probes (greedy).
- sherpa int8 decode of the same probes matches; `OfflineRecognizer.from_whisper` in eval/.venv, app decode shape (tail_paddings 1000).
- Tiled 67s probe (5 clips concatenated): the 30s window decodes 31 words across 4 sentences; no premature EOT (the per-tensor-int8 failure mode).
- fp32 vs int8 word divergence: 4.35% (23-word probe) and 6.67% (31-word tiled window), a couple of case-form words, no truncation or length collapse.
- Timestamps (the -attn contract): `enable_token_timestamps=True` returns real DTW timestamps on 81/81 tokens of the probe, monotonically increasing; encoder metadata `version 2`, `n_mels 128`, `model_type whisper-large-fi`, decoder has the 4 outputs including `cross_attention_weights`.
- Known deviation: `n_alignment_heads` is 320 (openai-whisper's default last-half-of-layers set) instead of a curated head list, because the hand-built .pt cannot carry the official checkpoint's alignment dump; this affects timestamp head count only, not WER.

## GO/NO-GO

**Qualified GO.** The quality case is made: 7.09 beats every measured incumbent including Turbo's 9.05, the model carries dual-bench published evidence plus third-party on-device evidence, the license is Apache-2.0, and the conversion lane is the proven whisper one. What is NOT yet proven is the device leg: 1.78GB of RAM-resident model and RTF 1.465 on a 4-thread desktop (3.5x Turbo's 0.413) must be shown workable on the RMX3853 before any catalog entry; a whisper-large decode that is slower than realtime on-device would be a poor default for voice notes even at 7.09. The Mozilla light-tier alternative (mozilla-ai/whisper-large-v3-turbo-fi, turbo class, card WER 11.97 CV-only) stays the fallback if the device pass fails.

## Device validation pass (RMX3853, 2026-11-03 evening)

Import driven through the app's own catalog dialog (fi language filter, Import, sha-256 verified on all three files, 1.78GB downloaded in about one minute over Wi-Fi). The RMX3853 (8GB RAM, Dimensity) loads and runs the model end to end:

- **Correctness:** FLEURS fi_fi_00 (12.3s) decodes to a transcript that matches the reference verbatim, with punctuation added by the polish pass ("Yhdysvaltojen ilmailuviranomainen väittää, että NextGen on järjestelmä...").
- **RAM:** measured load delta 705MB. The load spike triggered ColorOS lowmemorykiller kills of five background system services ("device is not responding" x5, "critical pressure") during the 21:28 load; the app itself survived and decoding continued. MemAvailable read 1.5GB after the run. This is the wall: on an 8GB device the model is usable but the load is invasive.
- **Speed:** pipeline total 58.5s for 18.6s of audio (RTF ~3.1 CPU; that total includes the two-pass refinement arm, so the bare whisper decode is somewhat faster than 3.1 but still clearly slower than realtime). Acceptable for voice notes, not a default-recommendation profile.
